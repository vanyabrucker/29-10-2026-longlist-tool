# Contacts Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Contacts (people at companies, and who at Helbling knows them) are readable across Helios: a Contacts page, contact pages, a Contacts card on company pages, a read-only Contacts column on longlists, and contact column blocks in the Excel export.

**Architecture:** Contacts are the corpus's existing `person` and `role` entities, plus a new `relationship` entity (child of a person) with one data point, `helbling_person`. A new `app/contacts.py` holds the one visibility rule (live observations, optionally as of a corpus version) and every contacts read. Lists get a real column `contacts` (source `contacts`) filled from the corpus at read time; existing lists get it through a data migration that writes one quiet version each.

**Tech Stack:** FastAPI, SQLAlchemy 2, Alembic, Postgres (pg_trgm already installed), openpyxl; Next.js 16, React 19, Tailwind v4, `motion`.

**Spec:** `docs/superpowers/specs/2026-11-20-contacts-design.md`

## Global Constraints

- No new dependencies (root AGENTS.md: human sign-off required).
- No fallbacks: missing or failing required things fail with a clear error.
- Before each commit: `helios-gateway/./scripts/check.sh` (needs `docker compose up -d`) for gateway changes; `helios-frontend/npm run check` plus a visual Playwright check (1440×900, DPR 2, throwaway script, system Chrome, not a project dependency) for UI changes. Fix every ruff/lint error.
- Frontend: Feather icons only (copy into `src/components/icons.tsx`); palette tokens only; buttons `rounded-full`; popovers `rounded-xl border-line p-1` soft shadow, 36px rows; UI text 13–15px; every string in `src/lib/i18n.ts` with a German translation (Swiss spelling, "Sie"). Data values (names, titles) are never translated.
- The relationship label is **"Known by"** (data point `helbling_person`, entity `relationship`). No kinds or strength.
- Read-only list error copy: `Contacts come from the corpus and can't be edited on a list.`
- Migration version: author `Helios`, message `Added the Contacts column`; `longlists.updated_at` unchanged.
- Export block headers, per contact N: `Contact person N name`, `Contact person N role`, `Contact person N phone`, `Contact person N email`, `Contact person N relationship`.
- Harness touched (`_read_list`): run `helios_scenarios` 3 epochs before (parent commit worktree) and after with the same models, record both with `uv run python -m evals.history --note "…"` (before first), report.

## Review Focus

1. A list import of an **outside** file with a header "Contacts" (or the export's contact block headers) must not write to or create a column clashing with the read-only Contacts column → test in Task 4.
2. **Reverting** the seed (or any import that made people) makes those contacts disappear everywhere: company page, `/contacts`, list cells, export → test in Task 3.
3. An **older list version** shows contacts as of its `corpus_version`: a contact added later is absent there → test in Task 4.
4. **Re-importing a full export** that has contact blocks reports "Nothing changed" → test in Task 6.
5. Contacts with **only some fields** (no email, no title, no Known by) render without "undefined"/empty separators, in cell, popover, pages and export → tests in Tasks 3 and 6, visual check in Tasks 8–10.

### Task 3: Contacts read API

**Files:**
- Create: `helios-gateway/app/contacts.py`

**Interfaces:**
- Consumes: `write_contacts`, `ContactSpec` (Task 2); `corpus.detail(session, entity_id)` builds `cells` for any entity.
- Produces:

```python
# One contact as every view gets it. `role` only in company-scoped results.
ContactItem = dict  # {"id", "name", "first_name", "last_name", "email", "phone", "linkedin",
                    #  "roles": [Role], "known_by": [Known], "role"?: Role}
# Role  = {"id", "company_id", "company_name", "title", "function", "primary": bool, "current": bool}
# Known = {"name": str, "email": str | None, "user": bool}

def company_contacts(session: Session, company_ids: list[uuid.UUID],
                     corpus_version: int | None = None) -> dict[uuid.UUID, list[ContactItem]]
def search_contacts(session: Session, q: str | None, offset: int, limit: int) -> tuple[int, list[ContactItem]]
def contact_detail(session: Session, person_id: uuid.UUID) -> dict  # 404 HTTPException if not a visible person
router: APIRouter  # GET /contacts?q=&offset=&limit= -> {total, offset, limit, items}; GET /contacts/{id}
```

Rules (one private helper computing shown values per entity, live or as of `corpus_version`, reusing `values.winner` and the `live()` rule from `longlists.corpus_cells` plus `Entity.created_version_id <= corpus_version`):
- A person is visible iff it has ≥1 live observation; a role iff its person is visible and it has ≥1 live observation; a relationship likewise.
- A role is current iff its shown `end_date` is empty or after today.
- `name` = shown `full_name`, else `first_name last_name` joined, trimmed.
- `known_by`: resolve each `helbling_person` value to a user by lower-case email, else case-insensitive exact `users.name`; `name` = the user's name when matched, else the value as written; dedupe by resolved identity.
- Company-scoped order: `primary` first, then name (case-insensitive). Search order: name.
- Search `q`: case-insensitive substring over shown name, email, title and the current companies' shown names (ILIKE over `current_values` joined to `observations`; no embeddings). `limit` 1–200, default 50.
- `contact_detail` = `{"id", "name", "cells": corpus.detail(...)["cells"], "roles": [Role + {"cells": …}] (current first, past too), "known_by": [Known]}`.
- `corpus.detail()` returns `"contacts": company_contacts(...)[company_id]` (empty list when none) in place of `"people"`; grep the frontend for `people` first to confirm nothing reads it.

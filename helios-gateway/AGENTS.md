# helios-gateway — project notes

Python FastAPI service that imports spreadsheets into the Helios master database or into a longlist, and serves both. Corpus imports are dev-only (the `/admin` area of `helios-frontend`); list imports are for everyone signed in. Prototype: synchronous design, no job queue.

## Run

```sh
docker compose up -d          # Postgres :5433 (pgvector image), S3-compatible store :9010
uv sync
uv run alembic upgrade head   # schema + source types
uv run python -m app.seed_users  # team accounts; passwords → .seed-users.local
uv run uvicorn app.main:app --port 8010 --reload --timeout-graceful-shutdown 3
uv run pytest                 # needs docker compose up; no LLM or embedding key needed
HELIOS_TEST_PG=postgresql://helios:helios@localhost:5434 uv run pytest  # another Postgres (with pgvector)
./scripts/check.sh            # ruff + pytest; run before every commit
uv run python -m tests.fixtures.make   # regenerate the sample files
uv run python -m evals.db refresh      # model benchmarks: see evals/README.md
```

`.env` (git-ignored) needs `EXPORT_SECRET` (32+ characters; signs exported workbooks), `DEEPSEEK_API_KEY` (imports), `AZURE_FOUNDRY_EMBEDDING_DEPLOYMENT_NAME` (a text-embedding-3-large deployment on the same Foundry endpoint; `AZURE_FOUNDRY_EMBEDDING_KEY`, its own key, no fallback; or `EMBEDDING_PROVIDER=openai-compatible` with `EMBEDDING_BASE_URL`/`EMBEDDING_MODEL`/`EMBEDDING_API_KEY`), `AZURE_FOUNDRY_ENDPOINT` / `AZURE_FOUNDRY_KEY` / `AZURE_FOUNDRY_DEPLOYMENT_NAME` (agent chat, default provider; `AGENT_LLM_PROVIDER=deepseek` switches the agent to `DEEPSEEK_API_KEY`) and `EXA_API_KEY` (web research); everything else defaults to the docker-compose services (see `.env.example`).

**Config must fail fast.** All settings live in `app/config.py` (`Settings`). Anything the server can't run without is checked in `Settings.problems()`, and `app/main.py` calls `config.check()` on import: startup exits with code 1 and one message listing every missing or invalid setting (no traceback). When you add a required setting, add its check there (and a case in `test_config_lists_every_problem`) rather than failing later at first use. Tools that don't serve requests (alembic, tests) don't run the check. Only config stops startup: a database or storage outage never does (the process stays up and readiness reports it).

**Health and version** (`app/health.py`, no gateway secret needed):
- `/health`: liveness, always `{"ok": true}`. It must stay instant and never depend on Postgres, storage or the LLM, so a platform never restarts the gateway over an outage it can't fix.
- `/health/ready`: `SELECT 1` on Postgres plus the schema revision, and `head_bucket` on storage, in parallel with a 2s timeout each. 200 with `{"db": "ok", "migrations": "ok", "storage": "ok"}`, otherwise 503 with the failing part as `down`/`behind` and the reason under `detail`. A missing bucket counts as ok (the first upload creates it). The local SeaweedFS accepts any credentials, so wrong S3 keys only show up against a real S3.
- The LLM is never health-checked: it costs money and fails on provider hiccups; a missing key is caught at startup.
- `/version`: package version (`pyproject.toml`), git commit and whether the gateway folder has uncommitted changes (`GIT_COMMIT` overrides both, for deployments without `.git`), catalogue version and migration head. MinIO no longer publishes community images, so SeaweedFS's S3 gateway stands in locally; any S3 service works.

## Decisions (agreed in the design session)

- **Fixed data model**, defined once in `app/catalogue.py` (data points with entity, type, options, description, synonyms, examples, half-life). The LLM maps against it; bump `CATALOGUE_VERSION` on changes. Entities: company, person, role (person at company), transaction, project_ref (children of a company), list_entry (a company on a longlist, holding relevance score/explanation). `sector`/`sub_sector` are free text until a fixed sector list is agreed.
- **Append-only observations**: every value is an `Observation` with source type, document, sheet/row/column, as-of date and version. Nothing is overwritten. The shown value per entity/field/fiscal year is the best **quality score** = source confidence × freshness (half-life per data point; undated counts half fresh; ties → newer version), kept in `current_values` and rebuilt after each change (`app/values.py`).
- **Source confidence** is fixed per source type (`source_types` table, seeded in the first migration).
- **Freshness date**: the import's as-of date, which the dev confirms (defaults to the file's last-modified date), never the upload date.
- **Versions**: each import is one global version; revert is a new version that marks that version's observations retracted (re-reverting re-applies). Any version can be reverted on its own. Original files stay in object storage.
- **Matching** (`app/ingest/match.py`): companies by registry/Capital IQ/Orbis ID or domain (certain), name without legal form + country (likely), fuzzy name ≥ 88 (suggestion only). People by email/LinkedIn (certain), name + company (likely). Duplicates within one file share one record.
- **LLM** (`app/llm.py`): imports use `complete_json` via `provider()` (DeepSeek by default: `LLM_PROVIDER` / `DEEPSEEK_API_KEY`). The agent uses `chat_provider()` for streaming tool-calling chat (`OpenAIChat`); default `AGENT_LLM_PROVIDER=azure_foundry` with `AZURE_FOUNDRY_*` (auth header `api-key`; Bearer also works), `deepseek` for DeepSeek's own API. Normalized stream events: `text_delta`, `tool_call`, `done` (with `latency_ms`), `usage`. Requests retry 429/5xx before anything has streamed: waits of 2, 5, 10, 20 and 30 s, each raised to the provider's reset time (`retry-after`, `retry-after-ms`, `x-ratelimit-reset-tokens`/`-requests`) up to 60 s, so at most 5 retries and about 5 minutes; then `LLMError` with `status` and a plain-English `user_message`. Cost per call comes from `TOKEN_PRICES_PER_M` (DeepSeek built in) or `TOKEN_PRICES` in `.env`; without a price it stays empty rather than guessed.
- **Agent chats** (`app/agent/`): an Anthropic-Managed-Agents-style harness run in-process. The UI only renders the event log.
  - **Tables:** `agent_configs` (versioned setup), private `sessions` (= Recents: owner-only, 404 for anyone else; `list_ids`, web approval fields, `web_searches_used`, status running/idle, stop_reason end_turn|requires_action|interrupted|error, `pending_tool_call_id`), append-only `session_events` (seq, type, payload, processed_at). Types: `user.message`, `user.interrupt`, `user.web_access` (the header's globe: `enabled`; no run starts, the agent reads a note), `user.tool_result` (a card's answer, with `granted` and `for_model`), `agent.message` (`step`, `interrupted` when cut short), `agent.tool_use`, `agent.tool_result` (`is_error`, `skipped`), `agent.model_usage` (provider, model, tokens, latency, cost per call), `session.status_running`, `session.status_idle` (stop_reason, plus the card for requires_action), `session.error` (`message` for the chat, raw `detail`).
  - **Config** (`config.py`): the prompt is `prompt.md`, the skills `skills/*.md`. `current_version()` hashes prompt, skill texts, tool names and model and creates a new `agent_configs` row (skill texts copied in) when they change, so editing a prompt needs no migration and a chat keeps the version it started with (its tool list too). Versions 1–3 predate this and hold skill names only.
  - **Loop** (`runner.py`, one daemon thread per running chat): `wake()` after the API commits a user event; a wake while the thread winds down makes it look again (no lost events). Every write is a short transaction (`_write`) that appends events and publishes them after commit; `events.append` locks the chat row, so the API and the thread can't take the same seq, and nothing holds that lock during a model call or a web search. Queued messages are marked handled when they enter the model's context, so each is answered once. `build_messages` puts every tool result right after its call and adds a placeholder for any call without one (stopped run, unanswered card), as the chat APIs require; tool results older than the last 6 are compacted (web hits to title and link, list reads to a note), except the newest `read_list` of each list since the last user message, which stays in full so the agent keeps the rows it is scoring or refining however many searches follow. Stop = `user.interrupt` + an in-memory flag: it ends the stream mid-way (the text so far is kept) or the run before the next tool call (the rest get skipped results). Deleting a running chat ends its run quietly. At most 24 model steps per turn. A restart marks running chats errored.
  - **Tools** (`tools.py`): one Pydantic model per tool is both the JSON schema the model sees and the validator; invalid arguments return a tool error with paths (`entries.2.relevance_score: …`). The only coercions are lossless: arguments as a JSON string (even twice encoded), a bare company name as a list entry. Each call runs in a savepoint, so a failed call leaves no writes (no half-made list); unexpected exceptions are logged and returned as tool errors. The same tool failing 3 times in a row is off for the rest of the run. Tools: `corpus_search` (empty = status ok + note, not an outage), `request_web_research` (approval card: one exact search, this run, or the chat), `web_research` (Exa, **off until approved** by clicking an allow button — typed text on the card is never consent; **20 searches per run**; run and one-search approvals end with the run), `read_list` (columns and rows with row ids), `create_list` / `update_list` (`add_row`, `set_cell`, `remove_row`, `add_column`, `remove_column`; columns by key or label; through `apply_changes`, author `agent`; filled-in facts get columns), `ask_user` (card title ≤ 120 chars, pauses with requires_action).
  - **Streaming:** `GET /sessions/{id}/stream?after=` subscribes to the in-process bus before reading the backlog and dedupes by seq; an async generator, so an open stream holds no thread and ends when the client goes away. Open streams keep a reload waiting, hence `--timeout-graceful-shutdown 3`. Text deltas (`agent.message_delta`) are live only.
  - Skills: `build_list` (intake → **scope buyer universe** → ask_user → internal first pass → approved web second pass), `refine_list` (read the list, then update it), `score_buyers` (how to score and explain a buyer: criteria by strategic/financial kind, ask for web research when inputs are likely missing, unknown is never 0, rationale with citations), `after_import` (after a chat import: read the list, say in a sentence or two what changed, then if relevance rationales or scores are empty ask whether to fill them, and fill only empty cells from internal data). Chat copy is plain English, no tool jargon. API: `GET/POST /sessions`, `GET/PATCH/DELETE /sessions/{id}`, `/events?after=`, `/messages`, `/tool_results`, `/web_access` (`{enabled}`: web search for the whole chat; a click, so consent like the card's allow button; off also drops run and one-search allowances), `/interrupt`, `/stream`. Tests in `tests/test_agent.py` use a scripted fake model (no real LLM or Exa).
- **Citations** (`app/citations.py`): agent text may hold `[[source | url | evidence]]` (url empty for internal data; split on the first two pipes). The tools check the syntax (`Entry.relevance_explanation`, `set_cell` on the rationale) and return a path-tagged error, so a broken marker is fixed by the model. Text stays plain strings everywhere; the frontend renders the markers as chips. Excel exports carry the raw markers.
- **Long steps** (imports and agent runs) run in a background thread in the API process. Imports write step/progress/ETA to the `imports` row (UI polls). A restart marks running imports failed and running chats errored.
- **One commit at a time** (Postgres advisory lock); if anything was committed since the report was built, the report is rebuilt and the dev reviews again.
- **Search** (`app/search.py`, `app/embeddings.py`): Postgres only (pgvector + pg_trgm), no separate engine. `company_search` has one row per company with its shown name, website, sector, sub-sector, HQ (plus its ISO `country`), description, latest revenue with its currency, employees, buyer category and investor type, a weighted `tsvector` ('simple' config: name and website A; sector, sub-sector, HQ and industry keywords B; description, products, services and investment focus C), GIN-indexed, `pg_trgm` indexes on the name and website, and `embed_text` (name, legal name, sector, keywords, buyer/owner type, value chain, HQ, description, products, services, business units, investment focus). `values.recompute` refreshes it in the same transaction as every import commit, pin and revert; each migration that changes the row query backfills with its own frozen copy.
  - **Embeddings** (`company_embeddings`: one `vector(1536)` per company with the model and the md5 of its text, HNSW cosine index) are made **right after commit, not inside it**: an embedding call is slow and can fail, and must never block or roll back an import, pin or revert. `search.refresh` marks the session; an `after_commit` listener wakes a background thread that embeds every company whose text hash or model differs (batches of 64, the model call outside any transaction); startup runs the same sweep. Until a company has a vector it is found by keywords only; a changed one keeps its old vector until the new one is in. Provider: `llm.embedder()` (`OpenAIEmbedder`, any OpenAI-compatible `/embeddings`; default a **text-embedding-3-large** deployment on the Azure AI Foundry resource, shortened to 1536 dimensions by the API). Search requests embed the query with `quick=True` (one try, 8 s timeout, cached); if that fails, search runs on keywords alone and says so (`mode: keyword`).
  - **Ranking:** two retrievers over the rows that pass the filters. Keywords: word prefixes (`isar cap` → `isar:* & cap:*`, only letters and digits pass, so input can't inject tsquery syntax), the website as typed, or a fuzzy trigram match on the name. Vectors: the nearest 100 within `VECTOR_MARGIN` (0.12) of the best similarity and above 0.30: text-embedding-3 scores all business texts 0.25–0.4 against each other, so an absolute cutoff keeps most of the corpus, while relevant hits sit close to the best (tuned on the eval set). Fused by reciprocal rank (k=60); exact name or website first, then names starting with the query, then the fused order. `total` is the size of that fused set. Filtered HNSW scans use `hnsw.iterative_scan = relaxed_order`.
  - **Filters** (`search.Filters`, SQL conditions on both retrievers; without a query they list every company that passes, by name): HQ countries (ISO codes) and region presets (`app/regions.py`: dach, benelux, nordics, eu, europe, uk_ireland, north_america, asia_pacific), sector words (whole words, case-insensitive, in sector or sub-sector; any of them), buyer category, investor types, revenue and employee ranges. **Currencies:** revenue is stored and shown as reported; there is no FX. A revenue *range* (millions of `revenue_currency`, default EUR) compares other currencies at fixed rounded rates (`APPROX_EUR_PER_UNIT`, dated), used only to decide whether a company falls in the range; a currency without a rate can't be compared and counts as missing. Companies without the figure fail a range unless `include_missing`. Revenue *sorting* still sorts amounts regardless of currency.
  - **API:** `GET /companies?q=&sort=&dir=&offset=&limit=&country=&region=&sector=&buyer_category=&investor_type=&revenue_min_m=&revenue_max_m=&revenue_currency=&employees_min=&employees_max=&include_missing=&mode=hybrid|keyword` (repeat list parameters) returns `{total, offset, limit, mode, items}`; unknown regions or country codes are 422. `GET /companies/facets` returns counts of HQ countries, sectors, buyer categories and investor types, the region presets and the currencies a range can use.
  - **Agent:** `corpus_search` takes the same filters as typed fields (`countries` ISO codes, `regions`, `sectors`, `buyer_category`, `investor_types`, `revenue_min_m`/`revenue_max_m`/`revenue_currency`, `employees_min`/`employees_max`, `include_missing`) and needs a query, a filter or both. Each result says how it matched (`words`, `meaning`, `words and meaning`); when nothing matched by words the tool says a company looked up by name isn't in our data (otherwise the model mistook semantic look-alikes for the target). The prompt and `build_list` tell the model to keep the query to what buyers do and put geography, size and buyer type in filters, one search per buyer angle.
  - **Evaluation** (`evals/`): `corpus.py` generates ~370 fictional companies (fixed seed; segments that matter for scoping plus look-alikes, a quarter of DACH descriptions in German, mixed currencies, some figures missing); `seed.py` imports them through the normal import flow (`uv run python -m evals.seed --embed`; dev databases only); `build_queries.py` writes `search_queries.json` (19 cases: the search as one text, the same as query + filters, and the expected companies from the generator's ground truth); `search_eval.py` prints recall@10 for text-only keywords (the old agent behaviour), keywords + filters, and hybrid + filters. At this commit: 0.16 / 0.45 / 0.99. The generated segments are cleanly separated, so hybrid's score is optimistic; add harder cases from real data when there is some.
- **Prioritizing a value** (`app/corpus.py`, `value_pins`): anyone signed in can prioritize one source of a data point over the quality score (`PUT /companies/{id}/pins` with field, period, observation_id) or hand it back to the score (`DELETE /companies/{id}/pins?field=&period=`). Pins are append-only events, each its own version (`kind = pin`, author = the user's email), so reverting it undoes it and the previous event decides again; an event without an observation removes the priority. `recompute` shows the newest live pin's observation if that observation is still live (reverting the import it came from hands the cell back to the score until re-applied); `current_values.pin_id` marks it. Both endpoints take the commit lock, so a pending import report goes stale and is rebuilt. `GET /companies/{id}` returns `cells` (per data point and period, catalogue order: shown value, score, level, confidence, freshness, as-of, `pinned` {by, name, at} and all live sources, the shown one first, each with label, category proprietary/internal/public, file/sheet/cell and its own score) plus the older `fields` (every observation, retracted ones too) for the admin view.
- **Scores are computed when read.** `current_values.score` is a snapshot from the last recompute and freshness decays daily, so the API scores shown values from source confidence and as-of date at request time. The level is Unknown when a value that goes stale has no as-of date. Note: internal files (0.7) sit right at the High threshold (70), so their values read Medium a day after their as-of date.
- **Round-trip exports** (`app/exports.py`): `GET /longlists/{id}/export` records a `list_exports` row (list, list version, corpus version, exporter, time, columns) plus `list_export_cells` (entry id, company id, column key, the value **as written** to Excel). The workbook has a very hidden `_helios` sheet holding `<export id>.<HMAC-SHA256 with EXPORT_SECRET, 32 hex>` and a hidden last column "Helios ID" with each row's entry id, inside the autofilter range so it moves when the user sorts. `verify()` rejects a tampered or foreign token; values are compared as written (`same()`: numbers by value, whitespace collapsed, dates by day), so money read back as a bare number still matches.
- **List imports** (`app/ingest/listdiff.py`): the same import stages and endpoints as corpus imports, with `imports.target = list` (`list_id` or `new_list_name`, optional `session_id` for a chat). Mapping: the "Helios ID" header and headers equal to the list's column labels map directly (`premap`); a verified export skips the LLM entirely (table detection too), otherwise the LLM suggests the rest; columns still open with values become a new list-only column (`new_column` + `new_label`); only company and list_entry data points are allowed. Matching: by entry id when the export mark verifies and belongs to this list, else by company with the corpus matcher (certain/likely), else list-only rows by name. Diff per cell (only non-unchanged cells are stored in the report): **unchanged** (file = list; or with an export, nothing changed on either side; without one, the file holds a value any export wrote before for that company/field) never writes, so the value keeps its provenance; **kept** (changed in Helios since the export) stays; **new/changed** writes: source `manual` (as of the file's date) when the uploader edited our export, `file` for outside data; **conflict** (both changed) is the reviewer's pick (`c:<row>:<column>` → file|helios, default helios). Exported rows missing from the file: `d:<entry id>` → remove|keep (default keep); only detected when the Helios ID column is present (the report's `export.has_ids` is false without it, and rows are then matched by company). Empty cells in an outside file are not deletions; corpus facts can't be emptied (error). Commit: one `apply_changes` call = one list version (new list: `create_list`), stale check against `base_list_version` (rebuilds the report like the corpus's `StaleReport`); "Nothing changed" commits with `list_version` null. Corpus columns that differ become prioritized observations exactly like a list edit (`edit_corpus`: source `manual` or `file`, the document id, revertable as a version); list-only and new custom columns keep provenance `file` (`{type, by, at, file}`). `source_types.file` = "Uploaded file", 0.5. **Where the data is from:** an outside file (no verified export of this list) gets a source in the mapping step, like a corpus import: `PATCH /imports/{id}` `source_type`, one of `IMPORT_SOURCES` (capiq, orbis, internal, crm, grasp, web, news, file, other; never manual or agent). `grasp` ("Grasp", 0.3 = Low, like the agent without a source): its data is web research and LLM output. `other` ("Other", 0.5) needs `source_note`, what the source is called (e.g. "Broker list"; 400 without it, and only `other` takes one); it can't be picked at upload. The note is never shown as a source: values read "Other". It is kept on the import, on each observation (`source_note`) and in list provenance (`note`), so a source named often can later become a source type of its own. `source_by` records who claimed the source (the uploader by default; observations `source_by`, provenance `claimed_by`). Cells the import writes carry the source type and its confidence (corpus facts as the observation's `source_type`, list-held values as provenance `type`). A verified export takes no source (409); its provenance logic is unchanged. Principle: a value never gains confidence by round-tripping through Excel. A chat import adds the list to `sessions.list_ids` and appends an unprocessed `user.import` event, then wakes the runner: like a message, it starts a turn (`build_messages` turns it into a note pointing at the `after_import` skill).
- **Longlists** (`app/longlists.py`, API in `app/longlist_api.py`): relational `longlists` (name, target, kind financial/strategic, owner email, head_version), `list_versions` (number per list, author email or "agent", message, `corpus_version` = global version at that moment, `reverts`, `changes`, `corpus_edits`) and `list_entries` (company_id, null for a row not in the corpus). Temporal, by row snapshot: `list_columns` (key, label, type, position, source `corpus:<field>` / `list` (relevance score and explanation) / `custom`) and `list_entry_states` (relevance_score and removed as columns, everything else in `data` jsonb). A change closes the current row (valid_to = N) and inserts a full new one (valid_from = N); unchanged rows aren't copied. Read N = valid_from <= N < valid_to (or null); diff N = rows ending at N paired with rows starting at N. **Every list write goes through `apply_changes(session, list, ops, author, message)`**, one new version per call (ops: add_entry, set, remove_entry, add_column, remove_column, order_columns, restore); "Nothing changed" is a 409 and makes no version. Restore N writes N's columns and states back as a new version; nothing is deleted. Corpus columns aren't copied: the latest version shows live values, an older one the values as of its corpus_version (a re-applied revert reads as if it never happened, since re-apply clears `retracted_version_id`). Editing a corpus fact from a list writes a `manual` observation (confidence 0.9, as-of today) plus a value pin in one global `manual` version (reverting it undoes both) and records the edit in the list version's `corpus_edits`, so the diff shows old → new; corpus facts can't be emptied from a list. Custom columns never enter the catalogue. Values a list holds itself (rows without a corpus company, custom columns, relevance) keep their provenance per cell in `list_entry_states.provenance` ({key: {type web|agent|manual, by, at, url?, title?}}; ops `add_entry`/`set` take an optional `source` {type web|agent|manual|file, url, title, as_of, file, document_id}, default agent for author `agent`, else manual; `add_entry` with `corpus: true` turns differing corpus facts into corpus edits, as list imports do); `table()` scores them like corpus values with the `web` (0.5), `agent` ("Agent, no source", 0.3), `manual` (0.9) or `file` (0.5) source type, and a value with no record is Unknown. Provenance isn't part of the diff or the change count. New financial/strategic lists put the main fact, then relevance explanation and score, right after the name. Imports with a list (`imports.list_id` or `new_list_name`) add their companies (relevance from `list_entry` cells) through `apply_changes` after the commit; a new list gets name, relevance and the import's mapped company fields as columns. Any signed-in user may read, edit, restore and export any list. Lists can't be deleted or archived. `GET /longlists` (most recently edited first), `POST /longlists`, `GET /longlists/{id}?version=&diff=`, `/versions`, `POST /changes`, `POST /restore`, `GET /export?version=` (.xlsx via openpyxl: shown columns in order, money as numbers with the currency in the number format; recorded and signed, see Round-trip exports). The migration moved the old `list_entry` entities into these tables and dropped `entities.list_id`.
- **Sessions commit before the response.** Use `Db` from `app/db.py` (`Depends(get_session, scope="function")`): FastAPI's default runs a yield dependency's exit after the response is sent, so the next request could miss the write (a fresh login token answered 401) and a failed commit went unnoticed.
- **Auth** (`app/auth.py`): email + password (stdlib scrypt hashes) against `users`; `POST /auth/login` returns a session token (only its SHA-256 is stored in `auth_sessions`, 30 days), sent back as `Authorization: Bearer`. `GET/PATCH /me` for the profile (name, language). Reading endpoints need any signed-in user (`SignedIn`); the import area needs `users.role = dev` (`Dev`, 403 otherwise). Roles are a ladder, member < admin < dev, each holding the rights of the ones before it (`User.is_admin` / `User.is_dev`), and its acting user is that user's email. The optional `GATEWAY_SECRET` (`X-Gateway-Secret`) is still checked on every request. Accounts come from `app/seed_users.py` (the Helbling team; existing users keep their password, `--reset EMAIL` issues a new one) or from admins: `GET /users` (any signed-in user), `POST /users` (admin; email + role member/admin; the generated password is returned only in that response) and `DELETE /users/{id}` (admin; not yourself, not a higher role; their sessions go with them). There is no self sign-up.
- **Model benchmarks** (`evals/`, see `evals/README.md`): Inspect AI (dev dependency only; the app never imports `evals/`) replays chosen real chats through the real harness to compare models. `evals.dataset export --chat ID` (or `--from` a "good chats" file; never all chats: they're private) reads the dev database read-only and writes `evals/data/dataset.jsonl`: the user's messages (with the header's web switch at each), card answers per kind in order, the original lists and usage; original web searches seed `evals/cache/exa.json`. `evals.db refresh` dumps dev into `helios_eval_base` (chats and logins removed, migrated); each run recreates `helios_eval` from it as a template, and the eval refuses any database not named `helios_eval*`/`helios_test*`. `evals/replay.py` creates a chat like the API, runs `runner.run_sync` (the loop without a thread) and plays the user: `ask_user` cards get the recorded answers in order, then "Use your judgement." (`fallback`); web cards get the recorded button (same consent), then the last one again, or "No" if the user never approved; the next message goes when the agent ends its turn. One model per process: `-T agent_model=deepseek[:model]|azure_foundry[:deployment]|fake` sets `AGENT_LLM_*` (so chats record the right config version); `llm.chat_provider_for(provider, model)` builds the judge. Web is cached by query (`record` default / `replay` / `live`). Scorers: harness numbers from the event log (tool error rate, calls, tokens, cost, time, list size, fallbacks), overlap with the original list, and a judge with `evals/rubric.md` (scoping, relevance, grounding, no invention; keep the judge fixed across compared runs). Inspect labels runs `helios/<agent_model>` through a never-called `ModelAPI`. A second task, `helios_scenarios`, runs hand-written scenarios with known answers (`evals/scenarios/*.jsonl`, fictional companies, committed): the chat starts on a list seeded from `setup.list` (list-only rows; a left-out field is unknown) and `filter_retention` checks that a filter keeps and flags rows whose deciding value is unknown instead of dropping them (`keep`/`flag`/`drop` by name). `scoring.jsonl` (`fit_scoring` + `scoring_judge` with `evals/rubric_scoring.md`) checks fit scores against Helbling's criteria: strategics on sector and size, sponsors on ticket and scope, VCs on stage; missing inputs stated and never scored 0; losses, foundation and listed owners kept as considerations; a second unit of one group flagged. Scenario scorers apply by the sample's `behaviour`. `python -m evals.report` prints the newest run per task and model as a Markdown table. `helios_eval.py` imports `app` at load because Inspect restores `sys.path` after loading the file. `tests/test_evals.py` runs the whole thing with the scripted `evals/fake.py` agent and judge. Real runs cost money: ask before running them.

## Import flow

Who: `target=corpus` (default) needs the dev role (403 otherwise); `target=list` is open to everyone signed in, who then see only their own list imports (others' imports are 404; devs see all, and `GET /imports` stays dev-only). List imports skip the duplicate-file check. List imports follow the same statuses; their report is `kind: list` (see List imports), corpus reports `kind: corpus`; both carry `totals` {new_rows, changed_cells, conflicts, errors}.

`POST /imports` (upload; 409 for a file uploaded before unless `allow_duplicate`) → `analysing` (parse, detect tables, store raw rows, LLM mapping) → `mapping_review` (dev edits: `PUT /imports/{id}/tables`, settings `PATCH /imports/{id}`, free-text `POST /imports/{id}/feedback` re-runs the mapping) → `POST /imports/{id}/report` → `report_review` (duplicates, matches, errors, quality, wins/loses vs current values; per-row decisions `PUT /imports/{id}/decisions`: `new` / `skip` / an entity id / `dup:<row key>`, and `<row key>:person` for the contact) → `POST /imports/{id}/commit` → `committed`. Revert with `POST /versions/{id}/revert` (dev only; works on imports, pins and reverts).

Edge cases: password-protected files are rejected; formulas use Excel's saved result and formulas without one are flagged; hidden sheets are skipped with a warning; macros are never run; `.xlsx/.xlsm/.xls/.xlsb/.ods/.csv` (CSV delimiter and encoding sniffed); placeholders like "n/a" or "Not disclosed" are empty; values that can't be parsed are errors in the report, never guesses.

## Layout

- `app/main.py` — import and version API. `app/embeddings.py` — company vectors after commit. `app/regions.py` — region presets and approximate rates for revenue filters. `evals/` — fictional corpus, search eval set and recall script. `app/exports.py` — recorded, signed list exports and value comparison. `app/corpus.py` — companies read API and pins. `app/longlists.py` / `app/longlist_api.py` — lists, versions, export. `app/agent/` — chat sessions, event log, tools, skills, SSE. `app/search.py` — company search index. `app/values.py` — shown values. `app/models.py` — tables. `app/catalogue.py` — data model. `app/llm.py` — import JSON LLM + streaming chat provider. `app/config.py` — settings.
- `app/ingest/` — `parse`, `detect`, `mapping`, `normalize`, `match`, `report` (corpus diff), `listdiff` (list mapping, diff and commit), `commit` (corpus commit), `runner` (stages for both targets).
- `evals/` — search recall eval (`search_eval.py` with `corpus.py`/`seed.py`/`build_queries.py`: generated companies, known answers) and model benchmarks on replayed chats (Inspect AI; dev only).
- `migrations/` — Alembic. `tests/` — unit tests, longlist tests, agent harness tests (`test_agent.py` with a scripted fake model), full-flow import test, search tests (`test_search.py`); `tests/fixtures/make.py` builds the sample files. Tests replace the embedder with a word-hashing fake (`conftest.FakeEmbedder`) and embed synchronously after each commit (`EMBED_IN_BACKGROUND=false`).
